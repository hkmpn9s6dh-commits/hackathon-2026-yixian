# 04 · 闸 C 证据（跑出来的，不是写出来的）

## 怎么复验

```bash
bash verify.sh        # 依赖 → 图版 → 分镜表 → 成片 → 47 条断言 → 证据帧
```

`scripts/verify.py` 的每一条都会打印 `PASS/FAIL`，并把结果写进 `proof/verify.log`；退出码 0 才代表全过。

| 组 | 条数 | 看什么 |

| AC-0…5 成片规格 | 9 | 存在、时长 60–240s、与 `story.py` 一致、1920×1080、H.264/yuv420p、≤400MB、AAC 48k 立体声、响度、真峰、LRA |

## 三个"这条断言救了一次"的地方

1. **AC-9b 第 1 秒必须有金线**：原来的开场是 13 秒黑场，线到第 1.2 秒才开始长、10.6 秒才走完。
   抽帧一看第 1 秒几乎是纯黑——直接判 FAIL。于是把线改成第 0.15 秒起、6.4 秒走完，开场缩到 10 秒。
2. **AC-10b 转场里金线真的在场**：`bloom` 模式下如果透明度淡得太快，转场就退化成"两个黑画面的溶解"。
   抽 6 处转场中点量金色像素，确认线是真的能被看见的。
3. **AC-11b 取样窗下边界**：工具水印在 `y ≥ 0.940`。任何一镜的 `cy` 只要往下多 3%，就会带出水印。
   这条把 20 个镜头的两个端点（`z0`/`z1`）全算了一遍。

## 全新 clone 抓到的三条（本机永远看不到）

本机的 `verify.log` 一直是 47/47 全绿，但**换一台机器从头 clone 就挂**。三条都是真的：

| # | 现象 | 根因 | 改法 |
| --- | --- | --- | --- |
| 1 | `verify.sh` 第 2 步就 FAIL：分镜表与 `story.py` 不一致 | `docs/03-SHOTS.md` 里写"图版 17 张"、列表却列了 18 个——生成器改过，文档没重生成 | 重跑 `scripts/gen_shots.py`（提交 `5f9533a`） |
| 2 | `AC-4 文件 ≤ 400MB` FAIL：410.2 MB | `build.py` 的压制是纯 CRF 21，这部片子颗粒重，实测冲到 **19 Mbps / 430 MB**；交付用的 193 MB 版本是另外一条命令压的 | `build.py` 加 `-maxrate 9M -bufsize 18M`（193.5 MB / 8.8 Mbps） |
| 3 | `AC-5d 真峰 ≤ −1.0 dBFS` FAIL：−0.6 dBFS | `audio.py` 按"AAC 只抬 0.4 dB"留的余量（峰值 0.82 ≈ −1.7 dBFS），实测这条 AAC 192k 抬了 **1.1 dB** | 峰值余量改 0.70（≈ −3.1 dBFS），编码后 −2.0 dBFS |

教训与赛道 T 那次同一条：**交付物必须由构建脚本产出**。凡是"手工再压一遍""另存一个 720p"得来的东西，
在 clone 里都会静默消失或换成另一个规格；只有 `bash verify.sh` 从零跑出来的那个文件才算数。
